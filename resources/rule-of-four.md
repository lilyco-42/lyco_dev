# 「四原则（Rule of 4）」与可维护性硬约束清单

所有受 `lyco_dev` (`/dev`) 约束的代码在提交前必须逐条通过以下检查：

## 1. 代码复杂度四原则
| 维度 | 硬上限 | 超限时如何重构 |
| --- | --- | --- |
| **类型成员变量** | ≤ **4** 个字段 | 拆分为语义清晰的子值对象组合（如 `User { identity, wallet, security, meta }`） |
| **函数参数** | ≤ **4** 个参数 | 封装为强类型 `Request` / `Config` / `Context` 结构体 |
| **逻辑嵌套深度** | ≤ **4** 层 | 使用卫语句（`let Some(x) = ... else { return Err(...); };`）与 `?` 展平 |
| **分支跳转** | 除错误处理外禁止随意跳转 | 禁止隐式 `continue/break/goto` 式多出口；只允许错误处理提前返回 |

## 2. 目录结构四原则（多维视角分类）
- **每个目录 ≤ 4 个子目录**，**总嵌套深度 ≤ 4 层**。
- 从 **前端 / 后端 / 数据库 / 代理端（网关）** 四个独立视角切分顶层边界：
  ```text
  project/
  ├── web/          # 前端（展示 + 简单消毒 + 类型契约转换，shadcn/ui）
  ├── server/       # 后端（纯数据处理、业务规则、强类型 API，绝不画 UI）
  ├── db/           # 数据库迁移、Schema 与原子事务层
  ├── gateway/      # 代理端 / 上游路由 / 熔断转发层
  ├── config/       # 外置 .toml 业务配置与 i18n/*.toml 语言包
  └── docs/         # 每次核心变更的目标与实现原理文档
  ```
  *(注：顶层如同时含 `config/` 与 `docs/`，可将业务代码归入 `apps/` 下 4 个子目录，保持任意单层子目录 ≤ 4。)*

## 3. 配置外置（TOML First）
- **禁止**在源码中把以下内容写死为常量：
  - 模型定价 / 费率 / 限流阈值 / 返佣比例 -> `config/pricing.toml`、`config/limits.toml`
  - 多语言文案（中文/英文等） -> `config/i18n/zh.toml`、`config/i18n/en.toml`
  - 上游端点与超时/重试策略 -> `config/upstreams.toml`
- 启动时将 `.toml` 反序列化为强类型配置结构体，缺字段或类型错立即抛出明确文件路径与字段名报错。

## 4. Git 提交与文档纪律
- **原子提交**：每完成一个最小可验证单元立刻 `git commit`，禁止攒几千行巨型提交。
- **Commit + Doc 双记录**：在 commit body 或 `docs/changes/` 中写明：
  1. **Goal（目标）**：本次改动解决什么商业/工程问题。
  2. **Principle（原理）**：核心数据流、类型边界与异常 Fallback 策略。
